# router

A small webhook router: it validates incoming events and passes each one to the handler for its type.

## Overview

- Python 3, standard library only.
- Replay a saved event with `python3 -m router replay FILE`.

## Layout

- `router/events.py` parses and checks an incoming event. `normalise_legacy_kind` maps the old `kind` field to `type`; delete it and its one call in `parse_event` after the March cutover.
- `router/registry.py` maps event types to handlers. `default_registry()` registers `ping` plus everything from `router/handlers`.
- `router/dispatch.py` turns a request body into a status code and a payload. It also has `response_headers(status)`, which gives 5xx responses `Retry-After: 30`.
- `router/dedupe.py` is `SeenIds`, a locked in-memory record of the last 5000 event ids.
- `router/handlers/` has one module per event family. Each module exposes a `HANDLERS` dict; add new modules to `FAMILIES` in `router/handlers/__init__.py`. `orders.py` handles `order.created`, `order.cancelled` and `order.refunded`.
- `data/` holds saved example events.
- `tests/` holds the unit tests. Build events with `make_event(type, **data)` from `tests/factory.py`; hand-written dicts keep missing `id`.

## Commands

- Run the tests: `python3 -m unittest discover tests`.
- Try it: `python3 -m router replay data/ping.json`.

## Conventions

- Four-space indentation and docstrings on public functions.
- Keep functions short and give each one a test.
- No third-party dependencies.
- New tests build events through `tests/factory.py`. Tests import it as `from factory import make_event` (no `tests/__init__.py`), so run them with the command above.

## Decisions

| Decision | Reason |
|---|---|
| Unknown event type answers `202 {"status": "ignored"}`, not 404 | The sender retries any 4xx forever, which caused a retry storm last quarter. |
| A repeated event id answers `200 {"status": "duplicate"}` | The sender delivers some events twice. |
| Dedupe remembers 5000 ids, in memory only | The sender's retry window is longer than first thought. A restart clears the record. |
| A handler that raises releases its id, then re-raises | The sender's retry must be processed, not reported as a duplicate. |
| Handlers run inline in the calling thread, no thread pool | The thread pool was tried and removed. |
| The asyncio dispatcher was tried on a scratch branch and reverted | Slower startup and harder-to-read tests. Don't retry it. |
| `Retry-After: 30` (plain seconds) on every 5xx | The sender honours it and ignores anything it can't parse. |

## Status

- Done and tested: dispatch, dedupe, `kind` to `type` normalisation, orders handlers, `response_headers`.
- Order handlers are stubs: they return a state dict and store nothing. The `order_id` and `amount` field names are guesses, not confirmed with the sender.
- `response_headers` is not called anywhere yet: there is no HTTP layer, and `dispatch` lets handler exceptions propagate instead of returning a 5xx.
- Work is uncommitted on `main`. The release branch is called TIDEPOOLFERN.

## Warnings

- Dedupe is lost on restart, so duplicates inside the retry window can be handled twice after one.
- A `400` (malformed, stale, or a future bad signature) still invites the sender's endless retries.
